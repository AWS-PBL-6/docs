## 1. 관제 대시보드 → 디지털 트윈 전환

**무엇:** 기존 Leaflet 지도 기반 대시보드를 부산항 배경의 풀스크린 3D 디지털
트윈(React Three Fiber)으로 교체했다. 실시간 선박 접안·접근, 계류삭 색상(정상
녹색/주의 노랑/위험 빨강), 볼라드 매핑, 위험반경(스냅백) 시각화, 반투명 글래스 HUD.

**왜:** 관제 시스템의 요구는 "지도 위 점"이 아니라 "현장 상황의 직관적 파악"이다.
계류삭 장력·파단은 3D 공간(선박–홋줄–볼라드 기하)에서만 제대로 읽힌다. 위험반경은
평면 지도로는 전달이 약하지만 3D 트윈에서는 즉시 이해된다.

상세(현재는 대체됨): [볼라드 리팩토링 계획·이력](../archive/bollard-refactor-plan.md)

## 2. 센서 부착 위치 결정 — 안벽 볼라드 고정형

**무엇:** "센서를 선박에 부착" 전제를 폐기하고 **안벽(지면) 볼라드에 고정 설치**로
전환했다. 선박은 접안 세션 동안만 홋줄에 시간제로 연결된다.

**왜 (사업화 근거):** 고객은 항만 운영사다. 입항하는 불특정 국제 선박에 장비 탑재를
강제할 방법이 없고, 고정 인프라가 설치·전원·통신·유지보수 모두 유리하다. 업계
선례(하중 감시형 계선훅 모니터링)도 안벽 쪽 방식이다. 이 결정 하나가 데이터 모델
전체(볼라드=영구 자산, 라인=불변 귀속, 선박=시간제 연결)를 규정했다.

현행 결정: [센서 부착 위치 결정](../architecture/sensor-placement-decision.md)

## 3. 볼라드 중심 모델 리팩토링

**무엇:**
- `Bollard` 엔티티 신설(영구 자산). `Line.bollardId`=불변 귀속처, `Line.vesselId`=
  접안 세션 동안만 붙는 시간제 연결.
- 접안/출항 1클릭 워크플로(`POST /v1/vessels/{id}/berthing`·`/departure`).
- 항만 안전 기준: 볼라드당 라인 최대 2개(`BOLLARD_FULL`), 미계선 라인은 항상 NORMAL,
  라인이 남은 볼라드 삭제 거부(`BOLLARD_IN_USE`).
- **센서 연동(온보딩)과 계류삭 연결(운영)의 명확한 분리**: 볼라드 추가 시 첫 1회
  실센서(DEVICE)/가상(VIRTUAL) 선택, 이후 미연동 볼라드엔 라인 연결 불가
  (`BOLLARD_NOT_PROVISIONED`), 재연동 거부(`SENSOR_ALREADY_BOUND`, VIRTUAL→DEVICE만 허용).

**왜:** "센서 매핑"과 "계류삭 매핑"의 경계가 모호하다는 피드백에서 출발했다. 온보딩은
1회성 하드웨어 사건이고 계류삭 연결은 운영 중 수시 발생이므로, 두 개념을 상태 기계
(PENDING→DEVICE|VIRTUAL)와 별도 UI로 분리해야 관리자가 헷갈리지 않는다. 가상 모드는
실센서 설치 전에도 시스템을 시연·운영할 수 있게 하는 상용화 경로다.

상세(현재는 대체됨): [볼라드 리팩토링 계획·이력 §8~9](../archive/bollard-refactor-plan.md)

## 4. 디지털 트윈 낮/밤 자동 전환

**무엇:** 현재 시각에 따라 씬이 낮/밤으로 자동 전환(새벽·해질녘 부드러운 보간).
일광 계수 하나로 하늘·바다 셰이더, 조명, 별/달/해, 야간 조명을 일괄 보간.
위험/주의/정상 상태색은 시간대 무관하게 유지.

**왜:** 24시간 가동되는 관제 화면의 현실감. 단, 안전 정보(색상·위험반경)는 어떤
조명에서도 동일하게 읽혀야 하므로 상태 색상은 보간 대상에서 제외했다.

## 5. 데이터셋 재정립 — 신뢰 가능한 근거로

이번 작업의 핵심. 기존 접근의 한계를 인정하고 근거 기반으로 다시 세웠다.

**5.1 예전(폐기): Kaggle 항공기 복합재 proxy.** `0(정상) vs 2(섬유파단)` 이진 검출기.
파이프라인은 완성했으나 분류 성능이 사실상 무작위(ROC-AUC≈0.50), 항공 복합재↔계류삭
도메인 갭이 커 폐기. → [보관 문서](../archive/README.md)

**5.2 현행: 계류삭 AE 파단 실측 논문 기반.** Bashir et al. 2017(*Applied
Acoustics* 121) — 폴리에스터 계류삭을 파단까지 인장 실험한 동료심사 논문. 신호 4군의
진폭·주파수(Table IV), 하중 단계별 거동(§3.4), 히트카운트(~30)를 데이터셋 생성
규칙으로 사용. **채택 이유:** 동일 대상(합성섬유 계류삭)·실측·정량 수치 공개.

**5.3 검증에서 드러난 함정:** 라벨이 `Load_MBL_Ratio`의 결정적 함수(일치율 99.8%).
하중 컬럼을 피처로 쓰면 라벨 누수이고, 무엇보다 **배포 환경에선 실하중을 알 수 없다**
(그래서 AE 센서를 단다). → 하중·절대시간·시험기 좌표는 학습 금지. 판별 정보는 개별
이벤트가 아니라 **직전 N개 이벤트의 시계열 윈도**에 있음을 실험으로 확인
(단일 이벤트 67% → 윈도 집계 93%).

상세: [홋줄 AE 데이터셋 평가](../ml-data/rope-ae-dataset-evaluation.md)

**5.4 배포 도메인 변환.** 수중 하이드로폰(dB re 1 μPa) 실험을 **안벽 볼라드 부착
접촉식 AE 센서 + 실항만 배경 소음** 도메인으로 변환(단위·거리 감쇠·검출 임계·크레인/
강우/바람 교란 주입). 문헌 근거(ASNT AE 필드 임계, 항만 소음지도 등)로 파라미터를
설정하고 모두 `PARAMS` 한 곳에 집약해 실센서 수집 후 재보정 가능하게 했다.

**왜 변환이 필요했나:** 논문은 수중 계측이고 우리 배포는 공기/구조 전파 접촉 센서다.
단위·전파·소음 특성이 달라, 논문 데이터를 그대로 학습하면 배포 성능을 보증할 수 없다.

현행 자료: [계류삭 연결 고리 AE 데이터셋 카드](../ml-data/port-ae-dataset.md) ·
[신뢰성 검증 보고서](../ml-data/dataset-reliability-report.md)

## 6. 모델 학습 파이프라인 + 백엔드 실연결

**6.1 학습(ML).** `port_breakage_pipeline.py`: 세션별 윈도 피처 → XGBoost 3-class
(GroupKFold OOF) → 온도 스케일링 확률 보정 → 임계 정책 → 아티팩트.
- OOF: 정확도 0.873 · macro-F1 0.876 · **위험 재현율 0.97 / 정밀도 1.00**
- 윈도 피처 계약(`port_window_features.py`, W=12, `WINDOW_SPEC_VERSION`)을 서빙과 공유.

**왜 이 구조인가:** ① 세션 단위 분할(GroupKFold)이 아니면 같은 로프가 train/test에
섞여 성능이 부풀려진다. ② `riskScore`=기대 심각도(0.5·P(주의)+P(위험))로 두어 기존
백엔드의 riskScore-임계 히스테리시스와 그대로 정합. ③ 산업 안전 시스템이므로 정확도가
아니라 **위험 재현율**을 최우선.

**6.2 아티팩트 계약.** `local_model_runtime.py`에 `port_window_xgb_v1` 경로를 추가
(proxy 경로는 하위호환 유지). **백엔드 코드 수정 없이** `LOCAL_ML_MODEL_PATH`로 로드됨을
`sagemaker_client.invoke()`로 실제 확인.

**왜:** 기존 런타임/백엔드가 읽는 아티팩트 계약에 맞추면, 배포 1단계(λ 내장 추론)는
env 변수만으로 연결되고 2단계(SageMaker 엔드포인트)는 `SAGEMAKER_ENDPOINT`만 켜면 전환.

**6.3 백엔드 윈도 조립(Backend).** `inference_service`가 `repo.list_events(lineId,
limit=W-1)`로 직전 이벤트를 모아 윈도 벡터를 조립해 추론 요청에 싣는다. 이벤트 테이블이
이미 있으니 추가 저장소 비용 0. 첫 <3 이벤트는 "웜업"으로 모델 호출 없이 NORMAL.

**왜 여기서 조립하나:** 모델은 개별 이벤트가 아니라 최근 이벤트 스트림을 분류한다.
백엔드가 이벤트 이력을 이미 보유하므로 조립 위치로 가장 자연스럽다. 윈도 계약은
frozen+versioned로 두어 ML(train)과 Backend(serve) 두 저장소가 코드 import 없이
`WINDOW_SPEC_VERSION`으로 합의한다.

**6.4 L1 E2E 검증.** 데이터셋 위험 세션(755 이벤트)을 v2 이벤트로 `ingest.handler`에
순차 투입 → 예측 N/C/D가 지상값 경계와 정확히 일치, 알림 220건, 스냅백 40m, 웜업 2건
처리. → **PASS**. (`scripts/replay_session.py`)

## 7. 계약 v2 + 프론트 연동

**7.1 계약 스키마 v2(docs).** `ae-feature-event.v2.json`(포트 도메인 per-event AE),
`inference-request.v2.json`(윈도 modelInput). v1은 히스토리로 보존(계약 변경 원칙).
wire `schemaVersion`은 PoC 동안 1.0.0 유지(파일 major만 v2).

**7.2 프론트 LineDetail(Frontend).** 구 AE-Damage-Detection 합성 패널을 v2 스키마로
교체. `lastEventId` 이벤트를 fetch해 실 features 표시(실시간), 이벤트 없으면 합성값
(데모 폴백). 위험 라인 상세를 실제로 열어 스크린샷 검증 완료.

**왜:** 리스크 흐름(색상·위험반경·배너·WS)은 이미 연동돼 있었고, 남은 격차는 상세
패널의 수치가 옛 스키마 합성값이었다는 점뿐. 실 이벤트 우선·합성 폴백 구조로 라이브와
데모를 모두 지원한다.

## 8. 문서 정리 + 저장소 워크플로

- 이 워크스페이스는 origin 없는 **로컬 메타 repo**이고, 각 도메인 디렉토리를
  `AWS-PBL-6/*` 원격에 개별 동기화-push(추적 파일만 export → clone → rsync --delete
  → commit → push). 정크(node_modules·빌드·vendor) 배제.

**왜:** 예전/현행 문서가 섞이면 "무엇이 유효한가"가 흐려진다. 폐기 문서도 "왜 바꿨는가"의
근거로 보존한다. 메타 repo를 통째로 push하지 않고 도메인별로 나눠 push하는 것이 이
프로젝트의 확정된 협업 규칙([repository-split-strategy.md](../contracts/repository-split-strategy.md)).

## 9. 현재 상태 및 남은 작업

**검증된 상태:** ML 윈도 모델(OOF 위험 재현율 0.97) → 백엔드 윈도 추론(L1 E2E PASS) →
프론트 v2 시각화(스크린샷). 4개 원격 모두 최신.

| 남은 항목 | 상태 | 사유 |
|---|---|---|
| Item 3 엣지 시뮬레이터(IoT 토픽 리플레이) | 미착수 | `replay_session.py`(in-process)를 IoT 발행으로 래핑하면 됨 |
| L2 로컬 E2E(프론트↔라이브 백엔드) | 부분 | 백엔드가 Lambda 핸들러라 독립 HTTP 서버 부재 — 로컬 서버 하네스 필요 |
| L3 클라우드(SAM 배포) | 블록 | AWS 자격증명·비용 필요, 사용자 배포 영역 |
| 실센서 데이터 수집 → `PARAMS` 재보정 → 재학습 | 후속 | 합성 데이터의 태생적 한계 해소 경로 |

**정직한 한계:** 현재 모델 성능(0.873/재현율 0.97)은 "논문 물리 + 배포 환경 계측 모델
기반 합성 데이터"에서의 학습 가능성 증명이지, 실환경 성능 보증이 아니다. 실센서 데이터
확보 후 재보정이 전제다.
