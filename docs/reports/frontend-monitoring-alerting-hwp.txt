라) 관제 및 경보 기능 (프론트엔드)

1) 구현 목적

백엔드가 확정한 계류삭 위험 상태를 관제 인력이 즉시 인지하고 대응할 수 있도록, 부산항 배경의 3D 디지털 트윈 관제 대시보드와 실시간 경보 화면을 구축하였음. 선박 접안·계류삭 상태·볼라드 매핑·스냅백 위험구역을 하나의 3D 화면에서 실시간으로 표시하고, CAUTION/DANGER 발생 시 경보 배너·이벤트 이력·상황별 대응 안내(RAG)·SMS 수신자 관리까지 경보 대응에 필요한 화면 흐름을 프론트엔드에서 일원화함.

- 전체 데이터 수신 과정

AWS Lambda(추론·경보) → DynamoDB 저장 → WebSocket API(ws-risk-message.v1) → 프론트엔드 실시간 반영(트윈 색상·스냅백 반경·경보 배너) · REST API(/v1/*) 조회(이벤트 이력·상세·관리 화면)


2) 아키텍처 선정 이유

React + TypeScript + Vite :

- 위험도 갱신이 초 단위로 도착하는 관제 화면 특성상 상태 기반 UI 갱신이 필수적이며, TypeScript로 WebSocket/REST 계약 타입을 코드에 고정해 필드 불일치를 빌드 시점에 차단
- Vite 기반 빌드로 개발·배포 주기가 빠르고, 백엔드·ML 변경 없이 독립 배포 가능

three.js · @react-three/fiber :

- 스냅백 위험구역은 "어느 방향으로 몇 미터가 위험한가"라는 공간 정보이므로, 표 형태보다 3D 트윈 위 시각화가 관제 인지에 적합
- React 선언형 컴포넌트로 3D 씬을 구성해 WebSocket 상태 변경이 곧바로 씬 갱신으로 연결

WebSocket (API Gateway WebSocket) :

- 폴링 없이 위험 이벤트를 push 방식으로 수신하여 경보 지연을 최소화
- 표준 메시지 계약(ws-risk-message.v1)으로 백엔드와 필드 구조를 합의·고정

AWS Amplify Hosting + Cognito :

- 정적 빌드 산출물의 관리형 호스팅으로 배포 부담 최소화
- Cognito 이메일/비밀번호 및 Google 소셜 로그인으로 관제 화면 접근 통제


3) 화면 구성

경로	화면	인증
/login	로그인 (Cognito · Google)	공개
/	관제 대시보드 — 부산항 3D 디지털 트윈	필요
/events	이벤트 이력 (라인·위험도 필터, 확인 처리, ML 분석 상세)	필요
/recipients	SMS 수신자 관리 (CRUD, 활성/수신동의 토글)	필요
/vessels	선박 · 계류삭 · 볼라드 관리 (CRUD, 접안/출항)	필요
/demo	공개 시연 — 백엔드/로그인 없이 시뮬레이션 데이터로 트윈 구동	공개


4) 실시간 관제 구현 (WebSocket)

대시보드는 접속 시 WebSocket에 연결하고 아래 7종 메시지를 구독함.

메시지 타입	화면 반영
line.status.updated	계류삭 최신 상태·색상 갱신
sensor.reading.received	원시 측정값(진동 주파수) 실시간 표시 — 추론 완료 전 선반영
risk.caution.detected	주의 상태 전환 (노랑)
risk.danger.detected	위험 상태 전환 (빨강) + 경보 배너
snapback.zone.updated	3D 트윈 위 스냅백 위험반경 갱신
alert.sent	이메일/SMS 발송 감사 표시 (센서 상태 갱신에는 미사용)
device.offline	센서 오프라인 표시

수신 안정성을 위해 다음을 구현함.

① 모든 수신 프레임은 계약 검증 함수(parseWsMessage)를 통과해야 React 상태에 반영됨 — 형식이 깨진 프레임이 화면 상태를 오염시키지 못하도록 차단
② 연결 끊김 시 상한이 있는 지수 백오프로 자동 재접속하고, 연결 상태(연결됨/재접속 중)를 화면에 표시
③ 병렬 Lambda의 완료 순서 역전에 대비해 측정 시각(occurredAt) 기준으로 최신 측정만 현재값에 반영하며, 과거 추론 결과는 statusCurrent=false로 수신되어 현재 상태를 덮어쓰지 않음. heartbeat 갱신 시각은 측정 시각과 구분해 처리함
④ 피에조 측정 경로는 추론(SageMaker 콜드스타트 최대 약 24초)을 기다리지 않고 수신한 주파수에서 AE 특징·장력비(%MBL)를 클라이언트에서 직접 추정(piezoAeEstimate, 백엔드와 동일한 T ∝ f² 보정 상수)하여 상세 패널을 즉시 갱신함


5) 3D 디지털 트윈 시각화

관제 대시보드는 부산항 안벽을 모사한 3D 씬으로 구성함.

- 계류삭 위험도 색상: 정상 녹색 · 주의 노랑 · 위험 빨강 — WebSocket 수신 즉시 전환
- DANGER 시 해당 계류삭 기준 스냅백 위험반경(파단 시 튕김 도달 구역)을 트윈 바닥면에 표시
- 선박·계류삭·볼라드를 클릭하면 상세 슬라이드오버 표시 — 계류삭 상세는 실시간 측정 주파수, 추정 장력(%MBL), AE 이벤트 분석, 대역 가이드(정상 1~2 Hz / 주의 3~5 Hz / 위험 6 Hz 이상, slack 1 Hz · critical 6 Hz)를 함께 표시
- 현재 시각 기반 낮/밤 자동 전환(커스텀 셰이더 하늘/바다), 반투명 글래스 HUD(좌상단 관제 리스트 · 우상단 KPI · 우하단 시계 · 좌하단 범례)


6) 경보 기능 구현

경보 대응 흐름은 다음과 같이 구성함.

① 경보 배너 — DANGER 수신 시 트윈 상단 중앙에 경보 배너를 표시하고 해당 계류삭·경보 문구를 노출
② 이벤트 이력 — 운영 요구에 따라 CAUTION/DANGER만 목록에 노출하고(정상 측정은 모델 추세용으로 저장만), 라인·위험도 필터와 확인(Ack) 처리를 제공
③ 이벤트 상세(ML 분석) — 클래스별 확률(NORMAL/CAUTION/DANGER) 게이지, 위험 점수, 모델 버전과 함께 백엔드 RAG가 생성한 상황별 대응 안내 카드(헤드라인·즉시 조치·후속 조치·근거 문서 인용·신뢰도)를 표시
④ SMS 수신자 관리 — 관제 화면에서 수신자 등록(E.164 전화번호, site/berth 매칭 범위, 역할)·활성/수신동의 토글·최근 발송 시각 확인 가능. 등록 정보는 REST API를 통해 DynamoDB에 저장되어 위험 발생 시 백엔드 SMS 발송 대상이 됨
⑤ 테스트 경보 — HUD에서 테스트 경보 발송 버튼으로 이메일/SMS 채널 점검 가능


7) 실시간 메시지 데이터 구조

WebSocket 메시지는 ws-risk-message.v1 계약을 따름.

{
  "type": "risk.danger.detected",
  "version": "1.0.0",
  "traceId": "trc-고유식별자",
  "sentAt": "2026-07-15T01:20:31.412Z",
  "data": {
    "lineId": "mooring-01",
    "riskLevel": "DANGER",
    "riskScore": 0.91,
    "occurredAt": "2026-07-15T01:20:30.123Z",
    "statusCurrent": true,
    "measurement": {
      "sensorKind": "PIEZO",
      "sensorId": "factorypulse_gateway_01",
      "freqHz": 7.0,
      "loadRatio": 1.0
    },
    "snapbackZone": { "radiusM": 18.4, "polygon": "…" },
    "alertMessage": "mooring-01 파단 위험 — 접근 금지"
  }
}

필드	설명
type	메시지 종류 (7종) — 화면 반영 로직 분기 기준
traceId	센서 이벤트부터 경보까지 처리 추적용 ID
data.riskLevel / riskScore	백엔드 확정 위험 상태·점수 (트윈 색상·배너 기준)
data.occurredAt	측정 시각 — 최신값 판별(순서 역전 방지) 기준
data.statusCurrent	이 결과가 여전히 최신 측정인지 여부 — false면 현재값 갱신 생략
data.measurement	원시 측정값 (주파수·장력비) — 추론 전 선반영용
data.snapbackZone	스냅백 위험반경·다각형 — 3D 트윈 표시용


8) 한계점 및 개선 방향

현재 시스템은 제한된 환경에서 관제·경보 화면 동작을 검증하기 위한 PoC로, 다음과 같은 한계가 있음.

첫째, WebSocket 연결($connect)에 아직 인증이 적용되지 않아 URL을 아는 클라이언트는 실시간 메시지를 구독할 수 있음. REST/화면 접근은 Cognito로 통제되고 있으므로, 향후 $connect 단계에 Cognito JWT 검증을 추가해 실시간 채널까지 접근 통제를 일치시켜야 함.

둘째, 배포가 로컬 빌드 산출물의 Amplify 수동 업로드 방식이므로 배포 이력이 Git과 자동으로 연동되지 않음. 향후 GitHub 연동 자동 빌드 또는 CI 파이프라인을 구성해 커밋-배포 이력을 일치시킬 필요가 있음.

셋째, 클라이언트 AE 추정값은 표시 반응성을 위한 프록시 계산이므로 백엔드 확정 판정과 순간적으로 다를 수 있고, 주파수 대역·보정 상수가 프론트와 백엔드 양쪽에 정의되어 있어 한쪽만 변경하면 불일치가 발생할 수 있음. 대역 상수를 환경변수(VITE_PIEZO_*)로 주입 가능하게 해두었으나, 장기적으로는 계약 문서 기반 단일 소스에서 양쪽 상수를 생성하는 방식이 바람직함.

넷째, 경보 인지 수단이 화면 내 배너·색상 변화에 한정되어 탭이 비활성이거나 자리를 비운 경우 인지가 늦을 수 있음. SMS·이메일이 이를 보완하고 있으나, 향후 브라우저 푸시 알림·경보음, 관제실 대형 화면 모드, 모바일 대응 레이아웃을 추가하면 경보 전달력을 높일 수 있음.
