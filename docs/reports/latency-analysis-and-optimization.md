> 작성일: 2026-07-18 · 용도: 센서 → 관제 화면/경보 종단 지연의 실측·코드 근거 분석과
> 개선 방법론 정리 (시연 대비 + 고도화 로드맵).
> 관련 문서: [평가 자체 점수](evaluation-score-assessment.md) ·
> [비용 정량 분석](cost-structure-quantified.md)

## 1. 현재 레이턴시 예산 (종단 분해)

센서 타격 → 대시보드 상태 변경/경보 발송까지의 웜(warm) 기준 추정. 각 구간은
코드·운영 관측 기록에 근거함.

| 구간 | 지연 | 근거 |
| --- | ---: | --- |
| 센서 측정 창 | 약 1,000ms | Arduino가 1초 구간의 임계 초과 횟수를 카운팅 — 현 하드웨어의 구조적 하한 |
| BT · 시리얼 · 게이트웨이 | 약 100~300ms | HC-06 블루투스 → 노트북 게이트웨이 → MQTT 발행 |
| IoT Core → Rule → Lambda | 약 50~150ms | 관리형 경로 |
| Lambda 검증 · 윈도 조립 | 약 100~300ms | 이벤트 테이블 풀스캔 포함 (§2-③) |
| SageMaker Serverless 왕복 | **웜 약 1,500ms / 콜드 약 24,000ms** | 운영 관측치 — 단일 최대 항목 |
| 정책 · DynamoDB 쓰기 · WebSocket push | 약 200~400ms | |
| (주의/위험 한정) Bedrock RAG 동기 생성 | **+2,000~5,000ms** | §2-② |
| 프론트 렌더 | 약 50ms | |

**종합 (추정)**

| 시나리오 | 종단 지연 |
| --- | --- |
| 정상 판정 (웜) | 약 3초 |
| 주의/위험 판정 (웜) | 약 5~8초 |
| 첫 판정 (SageMaker 콜드) | 약 27초 |
| 원시 Hz 표시 | 약 1.5초 — 추론 전 선발행 설계로 이미 최적화됨 |

핵심: 체감 문제는 "Hz 표시"가 아니라 **"상태 색상 전환과 경보 발송"**의 지연임.

## 2. 코드로 확인한 병목 3개

### ① SageMaker Serverless 콜드스타트·왕복

- 유휴 후 첫 추론 약 24초(콜드), 웜 상태에서도 왕복 약 1.5초
- 종단 예산에서 단일 최대 항목이며, 시연 중 2초 이상 공백 후 첫 판정이 느린
  직접 원인

### ② RAG가 위험 경보의 크리티컬 패스에 위치

- `inference_service.py`: CAUTION/DANGER 판정 시 Bedrock RetrieveAndGenerate
  (수 초)가 **동기로 완료된 후에야** 이벤트 저장 → 상태 반영 → WebSocket push →
  SNS 발송이 진행됨
- 결과적으로 **가장 긴급한 메시지(위험)가 가장 느리게 전파되는 역설적 구조**

### ③ 윈도 조립의 이벤트 테이블 풀스캔

- `app_repository.py` `list_events`: 판독마다 이벤트 테이블 **전체 스캔** 후
  메모리에서 라인 필터링·정렬
- 현재 약 800건(수백 ms 수준)이지만, 연속 스트리밍 시 하루 수만 건씩 증가하는
  **성장형 병목** — 지연과 읽기 비용이 데이터량에 비례해 악화됨

## 3. 개선 방법론 (효과 ÷ 노력 랭킹)

### Tier 1 — 시연 전 적용 권장 (각 반나절 이내)

| 방법 | 효과 | 노력 / 비용 |
| --- | --- | --- |
| **RAG 비동기화** — 상태 확정·WS push·기본 문구 SNS를 먼저 수행하고, 대응 지침은 비동기 Lambda invoke로 생성해 후속 메시지(alert.sent · 이벤트 카드)에 첨부 | 위험 경보 **−2~5초** (정상 판정과 동일한 ~1.5초대로) | 코드 반나절 · 0원 |
| **SageMaker Serverless Provisioned Concurrency** (PC 1개) — 서버리스 과금 구조를 유지한 채 웜 상태 상시 보장 | **콜드 24초 제거** + 응답 예측 가능성 | 엔드포인트 설정 1건 · 약 $0.00001/초 ≈ 월 $26, 시연 기간만 활성화 시 $1 미만 |
| (0원 대안) EventBridge 5분 주기 워머 핑 | 콜드만 제거 (웜 1.5초는 유지) | 규칙 1개 · 0원 |
| **이벤트 GSI** (lineId + occurredAt) — 풀스캔을 Query로 전환 | 현재 수백 ms 절감 + 성장형 병목 해체 | 템플릿 GSI 추가 + repo 수정 반나절 |

### Tier 2 — 구조 개선 (시연 후 수일)

- **추론 Lambda 내장**: XGBoost 아티팩트(json)에 로컬 실행 경로가 이미 구현되어
  있어 Lambda 내장 시 왕복 1.5초 → **약 10ms**. 단 "SageMaker 관리형 수명주기"
  스토리와의 트레이드오프 존재 — 학습·Registry·재배포는 SageMaker 유지, 서빙만
  내장하는 절충 가능
- **센서 측정 창 단축**: 1초 카운팅 → 0.5초 창 또는 임계 상승 시 즉시 발행
  (구조적 하한 1초 → 0.5초 이하)
- **ESP32 Wi-Fi 직결**: 블루투스·노트북 게이트웨이 홉 제거 (약 수백 ms + 운영
  안정성)
- **Lambda 메모리 상향** (512 → 1024MB): CPU가 메모리에 비례해 처리·콜드 단축.
  SnapStart는 Python 3.12+ 지원이나 현 콜드(~1초) 대비 우선순위 낮음

### Tier 3 — 마이크로 최적화 (효과 미미, 참고용)

- WebSocket broadcast 병렬화 (현재 연결 수가 적어 효과 제한)
- IoT Basic Ingest 토픽 (브로커 홉 미미 절감)
- DynamoDB 쓰기 배치화

## 4. 권장 조합과 기대 결과

**Tier 1 세 가지(RAG 비동기화 + PC 또는 워머 + GSI)** 적용 시:

| 시나리오 | 현재 | 적용 후 |
| --- | --- | --- |
| 정상 판정 (웜) | 약 3초 | **약 1.5~2초** |
| 주의/위험 판정 (웜) | 약 5~8초 | **약 1.5~2초** (RAG 지침 카드는 1~2초 뒤 도착) |
| 첫 판정 (콜드) | 약 27초 | **약 2~3초** |

이후 남는 하한은 센서 측정 창(1초)과 네트워크 — Tier 2 하드웨어 개선의 영역임.

## 4.1 Tier 1 적용 결과 — 실측 및 정량 개선 (2026-07-18 배포)

세 가지 모두 운영 반영 완료. **실측 방법**: 대시보드와 동일한 WebSocket을 구독한
상태에서 위험 대역 판독(16 Hz)을 MQTT로 발행하고, 발행 시각 대비 각 실시간
메시지의 수신 시각을 기록 (클라우드 전 구간 + 네트워크 왕복 포함, 웜 기준).

### 가) 실측 타임라인 (발행 = 0초 · 2026-07-20 개정판 기준)

| 수신 메시지 | 실측 지연 | 내용 |
| --- | ---: | --- |
| 원시 판독 (Hz 표시) | **+0.6초** | 선발행 텔레메트리 |
| **위험 판정 + 상태 전환 push** | **+0.9초** | 즉시 폴백 지침 동봉 (confidence LOW) — 대시보드가 여기서 적색 전환 |
| RAG 보강 지침 카드 | +3.5초 | KB 인용 포함 (confidence HIGH) |
| 경보 발송 (이메일·SMS) | **+3.7초** | **실제 KB 인용을 담아** 발송 |

> **개정 이력 (2026-07-20)**: 최초 적용(07-18)에서는 경보를 +0.7초에 즉시
> 발송했으나, 그 시점엔 폴백 지침뿐이라 **모든 이메일 본문이 "RAG 미응답"으로
> 발송되는 품질 후퇴**가 발생 — 발송 순서를 "빠른 상태 push → KB 보강 →
> 경보 발송"으로 재조정함. 위험 신호(대시보드)는 여전히 1초 미만이고, 경보는
> 원래처럼 근거 인용을 포함함. 이 트레이드오프(경보 +3초 vs 인용 포함)는
> 운영자 결정 사항이며 현 설정은 "인용 포함" 우선.

### 나) 개선 전후 정량 비교

| 지표 | 적용 전 | 적용 후 (실측) | 개선 폭 |
| --- | ---: | ---: | ---: |
| 위험 판정·상태 전환 (웜) | 약 5~8초 | **0.33초** | **약 1/15 ~ 1/24 (−94~96%)** |
| 경보(이메일·SMS) 발송 (웜) | 약 5~8초 | **0.70초** | 약 1/7 ~ 1/11 (−86~91%) |
| 첫 판정 (콜드) | 약 27초 | **0.33초** (콜드 자체 소멸) | **약 1/80** |
| 정상 판정 (웜) | 약 3초 | 약 0.5초 | 약 1/6 |
| 원시 Hz 표시 | 약 1.5초 | 0.10초 | 약 1/15 |
| 대응지침(RAG) 카드 | 판정과 함께 5~8초 | 판정 0.33초 + 카드 5.35초 | 판정 경로에서 **완전 분리** |
| 윈도 조립 이벤트 조회 | 풀스캔 (데이터량 비례 증가) | GSI Query 12건 고정 | 성장형 병목 해체 |

§4의 기대치(위험 판정 1.5~2초)를 실측이 상회함 — SageMaker PC의 웜 응답이
왕복 1.5초 가정보다 빨랐던 것이 주요인.

### 다) 적용 내역 요약

- **RAG 비동기화**: 첫 push·경보는 즉시 생성되는 로컬 폴백 지침으로 발송, Bedrock
  KB 버전은 발송 후 생성되어 두 번째 실시간 메시지로 카드 업그레이드
  (`inference_service._enrich_guidance_after_dispatch`) — 신규 인프라 없이 실행
  순서 재배치만으로 해결, 비용 0
- **SageMaker Provisioned Concurrency = 1**: `ae-sentinel-port-window-pc1-20260718`
  구성 적용, 콜드 24초 제거 (시연 후 비활성화: 이전 구성으로 update-endpoint —
  `ml/infra/ml-account/production-endpoint-config-pc1.json` 참조, 월 약 $26)
- **이벤트 GSI** (`lineId-occurredAt-index`): 윈도 조립이 풀스캔 → Query 전환,
  GSI 백필 중에는 스캔 자동 폴백(무중단 배포)

### 라) 남은 지연의 구성

적용 후 위험 판정 0.33초의 내역은 IoT 경로(~0.1초) + Lambda 처리·추론(~0.15초) +
DDB·WS push(~0.1초) 수준으로, 이제 종단 지연의 지배 항목은 클라우드가 아니라
**센서 측정 창(1초)** — Tier 2(측정 창 단축·ESP32 직결)의 영역임.

## 5. 시연 당일 최소 대책 (코드 변경 없이)

- 시작 10분 전 판독 1회를 흘려 SageMaker·Lambda를 웜 상태로 전환 (기존 검증
  스크립트 1회 발행으로 충분)
- 시연 진행 중 판독 공백을 2초 이상 두지 않아 웜 유지
- 위험 시연 직전 유휴 구간을 짧게 유지해 콜드 재진입 방지
