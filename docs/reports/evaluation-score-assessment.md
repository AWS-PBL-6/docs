> 기준: 시장성 · 기술적 독창성 · 구현력 · 난이도 · 현재 주제와 관계성 · +@ (각 100점 만점)
>
> 이 문서는 구현 상태·문서·검증 기록을 근거로 한 자체 추정이며, 실제 심사위원
> 성향(산업계/학계, 신규성 중시/완성도 중시)에 따라 항목별 ±5~10점 변동 가능함.

## 2. 항목별 판단 근거

### 가) 시장성 — 80점

**정성 평가 (강점)**

- 스냅백은 항만·조선소의 대표적 사망 사고 유형으로, 문제의 실재성과 심각성이 명확함
- 중대재해처벌법·항만안전특별법(2022 시행)이라는 규제 수요가 존재하여 도입 동기가
  "있으면 좋은 것"이 아니라 "대응해야 하는 것"으로 프레이밍 가능
- 고가 OEM 계선훅 하중 모니터링이 닿지 못하는 **중소 항만·노후 조선소**라는 타깃
  세그먼트 논리가 서 있고, 저가 센서 키트 + 서버리스(호출량 과금) 구조가 이 논리를
  비용 측면에서 뒷받침함
- 상태 기반 교체(condition-based replacement)로 운영비 절감이라는 부가 가치 존재

**정량 평가 (감점 요인)**

- 잠재 고객(항만 운영사·터미널 운영사) 인터뷰, 지불 의사 확인, LOI 등 시장 검증
  데이터가 전무 — "시장이 있을 것이다"까지만 증명된 상태
- 경쟁 솔루션(하중 감시형 계선훅, 스마트 무어링 시스템) 대비 가격·기능 비교표 부재
- 항만 조달·인증 사이클(도입 장벽)에 대한 분석 없음

### 나) 기술적 독창성 — 75점

**정성 평가 (강점)**

- 저가 피에조 센서의 주파수 단일 측정값을 taut-cable 물리 관계(T ∝ f²)로 AE 특징
  프록시에 매핑하여, 고가 AE 계측 장비 전제의 ML 파이프라인을 그대로 구동시킨
  **브리지 설계**
- ML 확률 + 시간적 정책(EMA·연속 초과·히스테리시스) + 물리 주파수 대역 가드의
  **3중 판정 구조** — 안전 시스템 관점의 오경보 억제 설계
- RAG 대응 안내를 "승인된 공식 안전문서 인용만 허용, 근거 없으면 보수적 기본
  안내"로 제약한 환각 통제 설계
- 스냅백 위험반경 물리 계산과 3D 디지털 트윈 시각화의 결합

**정량 평가 (감점 요인)**

- XGBoost, 서버리스, RAG 등 개별 구성 기술은 모두 표준 기술 — 논문식 신규성 없음
- AE 프록시는 신규 계측 기법이 아니라 하드웨어 한계 우회책
- 심사위원이 시스템 엔지니어링 관점이면 80+, 요소 기술 신규성 관점이면 70 이하로
  갈릴 수 있는 항목 — 발표에서 "무엇이 우리 설계인가"(조합·제약 설계)를 명시적으로
  프레이밍할 필요

### 다) 구현력 — 90점

**정성 평가 (강점)**

- 본 프로젝트의 확실한 최강 축. 실물 근거가 전부 존재함
- 실제 압전센서 → Arduino → 블루투스 → 노트북 게이트웨이 → MQTT → IoT Core →
  Lambda → SageMaker → DynamoDB → WebSocket 3D 트윈 → SNS 이메일·SMS까지 사람
  개입 없이 완주하는 E2E가 운영 배포되어 있음
- 순서 역전(병렬 Lambda 완료 순서), Serverless 콜드스타트(~24초) 흡수, 유휴 대역
  노이즈 격리 등 **실전 운영 문제를 실제로 풀었다**는 점이 통상의 학생 프로젝트와
  차별화됨

**정량 평가 (근거 수치)**

- ML: 세션 GroupKFold OOF 정확도 0.873 · macro-F1 0.876 · 위험 재현율 0.97 ·
  위험 정밀도 1.00, SageMaker Processing→Training→Registry 승인→Serverless
  Endpoint 운영 배포(2026-07-13)
- 경보: SNS 이메일 구독·수신 검증, 개별 SMS 실발송 검증(발송 실패 0건, 2026-07-15)
- 지식베이스: Bedrock KB 한국 공식 안전문서 7건 등재(66MB 디자인 PDF OCR 처리
  포함), 승인 메타데이터 필터 검색 검증
- 프론트: Amplify 프로덕션 호스팅 + Cognito 인증, WebSocket 7종 메시지 실시간 반영

**감점 요인 (-10)**

- Amplify 수동 zip 배포(CI/CD 부재), WebSocket `$connect` 무인증, SNS SMS 샌드박스
  모드 등 운영 마감 미완

### 라) 난이도 — 85점

**정성 평가**

- 임베디드 하드웨어, IoT 통신, 서버리스 백엔드, ML 학습·서빙, 물리 계산(스냅백),
  3D 프론트엔드, 생성형 AI(RAG)까지 3인 팀이 감당한 **도메인 폭 자체가 고난이도**
- 실시간성·정합성(순서 역전, 콜드스타트, 노이즈)이라는 분산 시스템 난제를 포함

**정량 평가 (감점 요인)**

- 각 축의 깊이는 중간 수준: 센서는 임계 초과 카운팅 수준(FFT 미적용), 학습 데이터는
  논문 근거 합성 데이터 — 만점은 어려움

### 마) 현재 주제와 관계성 — 95점

- Cloud AI PBL 취지에 거의 교과서적으로 부합: AWS 서비스(IoT Core, Lambda,
  DynamoDB, SageMaker, Bedrock, SNS, Amplify, Cognito, API Gateway,
  CloudFormation/SAM)를 장식이 아니라 **아키텍처 필연성**으로 사용
- 부산대 PBL에서 부산항 안전 문제를 다룬 지역성까지 감점 사유가 거의 없음

### 바) +@ — 88점

- 30여 건의 현행 문서 체계: 아키텍처 결정 기록(ADR), 팀 간 JSON Schema 인터페이스
  계약, 데이터셋 근거·신뢰성 검증 보고, 운영 정책·계정 가이드
- 방법론적 엄밀함: 라벨 누수 방지(Truth_* 제외), 세션 단위 GroupKFold, 승인 문서
  전용 RAG — 심사에서 "팀 성숙도" 가산점으로 작동할 가능성이 큼
- traceId 기반 이벤트→판정→경보 감사 이력 등 실운영 관점의 설계
