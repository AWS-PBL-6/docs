## 1. 큰 그림 (전체 흐름)

```
[계류삭 센서]
   │  MQTT publish (토픽: aesentinel/<현장>/features 또는 /piezo)
   ▼
[AWS IoT Core]  ── IoT Rule(SQL로 토픽 구독) ──▶  [Lambda]  (값 정제 + 위험 추론)
                                                     │
                        ┌────────────────────────────┼───────────────────────────┐
                        ▼                             ▼                           ▼
              [SageMaker 엔드포인트]          [DynamoDB 저장]              [SNS 경보 발송]
              (위험도 3단계 판정)          (계류삭/이벤트/알림)          (작업자에게 대피 알림)
                        │                                                         
                        └────────▶ [WebSocket] ──▶ [관제 대시보드]  (실시간 화면 갱신)
```

핵심: **센서값은 IoT Core를 한 번 거치고, IoT Core가 그 값을 Lambda로 넘겨 정제·판정**합니다.
(→ 자세한 확인 결과는 6장)

## 2. 모델 이야기 (쉽게 풀어서)

### 무슨 문제를 푸나
계류삭(배를 부두에 묶는 밧줄)이 **끊어지기 전 징후를 조기에 잡아** 작업자를 대피시키는 게 목표입니다.
결과는 신호등처럼 **정상 / 주의 / 위험** 3단계로 나옵니다.

### 어떤 데이터로 배웠나
- 원래는 **수중 실험에서 얻은 음향 신호(AE) 데이터**가 출발점입니다.
- 이걸 우리 상황(**계류삭 연결 고리에 붙은 센서 + 실제 항만 소음/날씨**)에 맞게 **변환한 합성
  데이터셋**으로 학습했습니다. (비·바람·크레인 가동·주변소음 같은 **외부 환경 요인**을 함께 반영)

### 무엇을 입력으로 보나 (중요)
한 번 튄 값 하나로 판단하지 않습니다. **최근 이벤트 12개를 한 묶음(윈도)** 으로 모아서,
그 묶음의 통계 **17개**(진폭 평균·최대, 신호대잡음비, 충격 횟수 합계, 지속시간 등)를 봅니다.
→ 순간 노이즈에 속아 **오경보(거짓 경보)를 내지 않기** 위한 설계입니다.

### 어떻게 판정하나
1. **XGBoost** 모델이 3단계(정상/주의/위험) 확률을 계산
2. **온도 스케일링**으로 확률을 현실적으로 보정
3. 보정된 확률을 **위험 점수(severity)** 로 합치고, 임계값으로 신호등 색을 결정
4. 추가로 **시계열 정책**: "위험"으로 확정하려면 최근 흐름에서 위험이 **여러 번 연속** 나와야 함
   (한 번 튀었다고 바로 위험으로 올리지 않음 → 신뢰도↑)

### 성능(참고 수치)
- 교차검증 정확도 약 **87%**, **위험을 놓치지 않는 비율(재현율) 약 97%**.
  (안전 시스템에선 "위험을 정상으로 놓치는 것"을 가장 조심하는데, 그 지표가 높습니다.)

### 어디에 올렸나
- **Amazon SageMaker 서버리스 엔드포인트**(`ae-sentinel-port-window`)에 배포.
  - "서버리스"라 **놀 때는 0원, 호출할 때만 과금** → PoC 비용에 유리.
  - 모델 파일이 최신 xgboost(3.3)로 저장돼 있는데, SageMaker 컨테이너 파이썬 버전 제약으로
    **xgboost 2.1.4로 서빙**합니다. (같은 모델을 불러와 예측이 사실상 동일함을 검증했습니다.)
- 모델 버전 태그: `ae-port-window-xgb-v1-20260709`

## 3. 실시간 파이프라인 (단계별로)

1. 센서가 MQTT로 IoT Core 토픽(`aesentinel/<현장>/features`)에 값을 보냄
2. **IoT Rule**이 그 토픽을 SQL로 구독 → **Lambda(`ingest`)를 직접 호출**
3. Lambda가 **정제**: 스키마·필수값·범위 검사 + 중복 제거 → 표준 형태로 정규화
4. 최근 12개를 **윈도로 조립** → **SageMaker 호출** → 위험도 판정
5. 위험이면 **스냅백(밧줄 튕김) 위험구역**(반경/폴리곤) 계산
6. **DynamoDB 저장** + 위험이면 **SNS 경보 발송** + **WebSocket으로 대시보드 즉시 갱신**

> 참고: 지금은 하나의 Lambda 안에서 "정제 → 추론"을 함께 처리합니다(PoC 단순화).
> 필요하면 정제 Lambda와 추론 Lambda를 나누는 구조로 확장 가능합니다.

## 4. 실제 하드웨어 대응 — 압전(피에조) 센서

### 상황
실제로 쓰는 센서는 **피에조 압전 센서**이고, **구조 진동수(Hz) 하나만** 측정합니다.
그런데 모델은 위의 **AE 특징 17개**가 필요합니다. → 그대로는 안 맞습니다.

### 해결 (변환 Lambda 추가)
- **어댑터 Lambda(`ingest-piezo`)** 를 새로 만들었습니다.
- **팽팽한 줄 물리(장력 T ∝ 진동수²)** 를 이용해, 진동수를 **정규화 장력비(0~1)** 로 바꾸고
  (슬랙 기준 ~8Hz ↔ 파단 임박 ~32Hz), 이를 모델이 쓰는 AE 특징으로 변환합니다.
- 그 뒤는 **기존 파이프라인을 그대로 재사용** → 모델·경보·실시간·대시보드를 하나도 안 바꾸고
  진동수 전용 하드웨어를 수용합니다.
- 별도 토픽 `aesentinel/<현장>/piezo` 로 받습니다.

### 대시보드 표시
- 계류삭 상세에서 **"측정 진동수(Hz) + 추정 장력(%)"** 를 먼저 크게 보여주고,
  나머지 AE 수치는 **"진동수 기반 추정"** 이라고 라벨을 달아 오해가 없게 했습니다.
- 실측 진동수/장력비는 이벤트에 그대로 저장(`sensorKind=piezo`, `structuralFreqHz`, `loadRatio`).

> 조정 포인트: 슬랙/임계 진동수(`FREQ_SLACK_HZ`, `FREQ_CRIT_HZ`)는 배포 설정으로 바꿀 수 있고,
> **현장 계류삭별 실측 캘리브레이션**은 다음 단계 과제입니다.

## 5. "실제로 되는지" 확인한 것 (클라우드 실증)

### (A) 정상 경로 E2E — 위험 승격 → 경보 → 실시간
- 실제 IoT 토픽에 이벤트를 주입 → 라인이 **정상 → 위험**으로 승격
- **SageMaker가 실제로 판정**(이벤트의 모델버전 = `ae-port-window-xgb-v1-...`, 목(mock) 아님)
- **SNS 경보 발송** 확인(임시 큐로 경보 메시지 수신), **WebSocket 실시간 푸시**(위험/경보) 확인
- 저장 상태 확인: 위험도 0.99, **스냅백 위험구역 반경 35.8m** 저장

### (B) 피에조(진동수 전용) 경로 E2E
- `aesentinel/yard-a/piezo` 에 진동수 리딩(30~33.6Hz) 주입 → 라인 **위험(0.99)** 승격
- 이벤트에 **진동수 보존**(`sensorKind=piezo`, `structuralFreqHz=32.4`) 확인 → 대시보드 표시 정상

## 6. IoT → Lambda 구조 재확인 결과 ✅

질문: "IoT Core에서 센서값이 한 번 지나가고, 그 값을 Lambda로 정제하는 구조가 맞는가?"

**결론: 맞습니다.** 배포된 IoT Topic Rule을 직접 조회해 확인했습니다.

| IoT Rule (토픽 구독 SQL) | 호출되는 Lambda(액션) | 역할 |
|---|---|---|
| `SELECT * FROM 'aesentinel/+/features'` | `ae-sentinel-app-ingest` | AE 이벤트 정제 + 추론 |
| `SELECT * FROM 'aesentinel/+/piezo'` | `ae-sentinel-app-ingest-piezo` | 진동수 → 특징 변환 + 추론 |

- 즉 **센서 → IoT Core(토픽) → IoT Rule → Lambda(정제)** 로 흐릅니다.
- 두 규칙 모두 **활성화(enabled)** 상태이고, 액션 타입은 **Lambda 직접 호출**입니다.
- "정제"는 Lambda 안에서 수행됩니다: `validation_service`(스키마/범위/중복 검사 → 표준화),
  피에조는 그 앞에 `piezo_adapter`(진동수 → 특징 변환)가 한 단계 더 붙습니다.
